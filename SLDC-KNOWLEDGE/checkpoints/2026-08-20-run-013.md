## Sources inspected

### The Update Framework (TUF) — official project/specification

- Roles and metadata: https://theupdateframework.io/docs/metadata/
- Security: https://theupdateframework.io/docs/security/
- Specification v1.0.26: https://theupdateframework.github.io/specification/v1.0.26/

Verified:

- required top-level roles are Root, Targets, Snapshot and Timestamp;
- metadata is signed, versioned and expiring;
- target hashes/sizes, snapshot consistency and timestamp freshness form separate checks;
- the specification includes explicit defenses/checks for rollback, freeze, mix-and-match, arbitrary-software and wrong-software attacks;
- persisted trusted metadata/version state is part of rollback detection.

Caveat:

- TUF is an update trust/freshness framework, not evidence of post-install application health or generic binary/data rollback.

### Microsoft Windows MSIX / App Installer — official Microsoft documentation

- MSIX signing overview: https://learn.microsoft.com/en-us/windows/msix/package/signing-package-overview
- End-to-end MSIX signing: https://learn.microsoft.com/en-us/windows/msix/package/sign-msix-package-guide
- Auto-update/repair overview: https://learn.microsoft.com/en-us/windows/msix/app-installer/auto-update-and-repair--overview
- App Installer update settings: https://learn.microsoft.com/en-us/windows/msix/app-installer/update-settings
- Distribution path guidance: https://learn.microsoft.com/en-us/windows/apps/package-and-deploy/choose-distribution-path

Verified:

- deployable MSIX packages require a valid code-signing signature and device trust;
- `.appinstaller` supports non-Store auto-update behavior;
- launch/background update checks and activation-blocking policy are documented;
- `ForceUpdateFromAnyVersion` explicitly permits both upgrade and downgrade package transitions;
- current auto-update/repair documentation applies to Windows 10 version 2004/build 19041 and later and Windows 11, while individual settings document their own minimum Windows versions;
- self-signed signing is not a public production trust baseline.

Caveat:

- package downgrade capability does not establish database/configuration/remote-side-effect downgrade safety or post-update health.

### Sparkle 2 — official maintainer documentation

- Main documentation: https://sparkle-project.org/documentation/
- Publishing: https://sparkle-project.org/documentation/publishing/
- Security/reliability notes: https://sparkle-project.org/documentation/security-and-reliability/
- Upgrading: https://sparkle-project.org/documentation/upgrading/
- Delta updates: https://sparkle-project.org/documentation/delta-updates/

Verified:

- Sparkle 2 provides macOS appcast-driven update flows;
- maintainers recommend HTTPS, Developer ID code signing/notarization where applicable, and EdDSA signatures for update payloads;
- `generate_appcast` can generate appcast metadata/signatures and delta information;
- signed feeds are optionally supported with `SURequireSignedFeed` and require pre-extraction verification;
- delta updates fall back to full updates when unsuitable/unavailable;
- Sparkle 2 migration documentation states that downgrade support from Sparkle 1 was removed;
- maintainers recommend update testing with actual old/new application versions.

Caveat:

- no generic automatic post-install rollback capability was established from the inspected Sparkle sources.

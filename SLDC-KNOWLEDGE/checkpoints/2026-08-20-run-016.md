## Evidence added

### GitLab batched background migrations

Source type: official maintainer documentation.

Verified 2026-08-20:

- intended for long-running data migrations that exceed ordinary migration time limits, including high-traffic tables;
- explicitly not intended for schema migrations;
- jobs are batched, retryable and expected to be idempotent;
- timeout failures can be split into smaller batches;
- batch sizing is adjusted from recent execution efficiency;
- database-health checks can pause migration work using signals including WAL archival backlog/rate, active autovacuum and Patroni Apdex/SLO degradation;
- migration code is isolated from mutable application models because deployments can continue while the backfill runs;
- dependent behavior must not assume all data is migrated until an explicit finalization/completion gate succeeds.

Source:

- https://docs.gitlab.com/development/database/batched_background_migrations/

### Debezium 3.4 incremental snapshots + CDC

Source type: official project documentation.

Verified 2026-08-20:

- ad hoc incremental snapshots can run while CDC streaming is active;
- tables are reread in chunks rather than one monolithic blocking snapshot;
- source signaling plus watermarking is used for supported connectors to reconcile snapshot/change overlap;
- snapshots can be selected, stopped, paused and resumed subject to connector-specific support;
- PostgreSQL documentation distinguishes incremental from blocking snapshots, with blocking snapshots temporarily stopping streaming;
- support and prerequisites vary by connector, so capability is not generalized beyond documented scopes.

Sources:

- https://debezium.io/documentation/reference/3.4/configuration/signalling.html
- https://debezium.io/documentation/reference/stable/connectors/postgresql.html

### AWS DMS full-load + CDC

Source type: official AWS documentation.

Verified 2026-08-20:

- full-load-plus-CDC captures source changes during initial load, applies cached changes, then continues ongoing replication;
- CDC-only can be combined with another bulk-load mechanism;
- AWS explicitly states DMS CDC is not real-time and gives no SLA for CDC latency;
- transactional consistency is scoped within a task, which constrains how tables participating in common transactions may be split for parallelism;
- parallel full-load settings can multiply resource use and exhaust task memory;
- source scans/log capture create real load and lag depends on workload/network/replication/target capacity;
- rapid DDL/DML/DDL sequences during CDC are documented as a data-loss/unexpected-behavior risk for supported DDL replication paths;
- validation is a separate source-target evidence plane and is not equivalent to replication task health.

Sources:

- https://docs.aws.amazon.com/dms/latest/userguide/CHAP_Task.CDC.html
- https://docs.aws.amazon.com/dms/latest/userguide/CHAP_Introduction.Components.html
- https://docs.aws.amazon.com/dms/latest/userguide/CHAP_BestPractices.html
- https://docs.aws.amazon.com/dms/latest/userguide/CHAP_Tasks.CustomizingTasks.TaskSettings.FullLoad.html
- https://docs.aws.amazon.com/dms/latest/userguide/CHAP_Introduction.SupportedDDL.html
- https://docs.aws.amazon.com/dms/latest/userguide/CHAP_Validating.html

## Research additions

### Linux `perf` / `perf_events`

Verified from current Linux kernel/man-pages documentation:

- `perf` is based on the kernel `perf_events` interface and is intended for system/application performance analysis.
- `perf_event_open()` supports counting and sampled events through event file descriptors.
- Perf-event monitoring has explicit access/security boundaries.
- `CAP_PERFMON` is the least-privilege capability intended for performance monitoring; broad `CAP_SYS_ADMIN` is discouraged where `CAP_PERFMON` suffices.
- `perf_event_paranoid` changes unprivileged monitoring scope.
- Perf data can expose sensitive paths, identifiers, addresses/register state and potentially process data; performance artifacts therefore require security handling.

Sources, verified 2026-08-20:

- Linux kernel official: https://docs.kernel.org/admin-guide/workload-tracing.html
- Linux kernel official: https://docs.kernel.org/admin-guide/perf-security.html
- Linux man-pages project: https://man7.org/linux/man-pages/man2/perf_event_open.2.html

### Linux eBPF continuous profiling / Grafana Pyroscope

Verified from current Grafana documentation:

- Pyroscope is a continuous-profiling aggregation system with historical/time-range and metadata dimensions.
- Grafana Alloy can collect Linux CPU stack samples with its eBPF profiler without application source modification for supported targets.
- Current setup requires Linux kernel >= 4.9 for `BPF_PROG_TYPE_PERF_EVENT` and requires privileged/root host access for this collector path.
- eBPF auto-profiling is CPU-focused and does not replace all runtime/SDK-native profile types.
- Continuous profiles can be compared across time/labels and correlated with metrics/logs/traces.

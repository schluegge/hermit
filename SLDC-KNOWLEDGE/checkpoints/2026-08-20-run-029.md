3. NixOS generations.

## Primary/current evidence inspected

### rpm-ostree

Official upstream documentation:

- https://coreos.github.io/rpm-ostree/administrator-handbook/
- https://coreos.github.io/rpm-ostree/

Verified claims used:

- `rpm-ostree upgrade` stages an offline deployment for the next boot;
- `rpm-ostree rollback` swaps back to the retained prior deployment;
- `rpm-ostree deploy <version>` can select a historical version where history exists;
- package layering/overrides construct deployments rather than mutating the booted root in the conventional package-manager sense;
- the project describes transactional/versioned/checksummed OS upgrades and states that development focus for new bootable-container features has shifted toward bootc/dnf while rpm-ostree remains supported;
- OS rollback does not imply rollback of mutable user/application state.

### bootc / bootable container images

Official/upstream documentation:

- https://bootc-dev.github.io/bootc/man/bootc-fetch-apply-updates.service.5.html
- https://containers.github.io/bootable/how-does-it-work.html
- https://containers.github.io/bootable/what-needs-work.html

Verified claims used:

- bootable-container images are OCI images containing operating-system userspace/kernel/system manager and can be produced by normal container-image pipelines;
- update discovery/fetch/apply are separable through `bootc upgrade --check`, `bootc upgrade`, and `bootc upgrade --apply`;
- the upstream automatic update service can check the registry, fetch a newer image and reboot;
- previous bootable OS image recovery is documented through the boot loader;
- `/etc` and `/var` are generally persistent per-system state rather than replaced image payload;
- converting a non-bootc stock system to bootc is not documented as reversibly returning to that old stock-system behavior;
- the bootable-container project documentation explicitly states that the complete cryptographic trust chain from hardware through applications is not yet fully implemented in the described project state.

### NixOS

Official/current project documentation:

- https://nixos.org/manual/nixos/stable/
- https://nixos.org/guides/how-nix-works/
- https://wiki.nixos.org/wiki/Nixos-rebuild

Verified claims used:

- declarative configuration builds new system generations instead of overwriting the prior system closure;
- `nixos-rebuild build`, `test`, `boot` and `switch` provide distinct build/activation boundaries;
- `nixos-rebuild switch --rollback` can select the previous generation;
- previous generations can remain selectable from the bootloader;
- deleting old generations removes future rollback capability;
- the manual warns that a Nix database-schema upgrade can make switching back to an older channel nontrivial, so generation rollback is not a universal reversal of every state/schema transition.

## Contradiction / falsification pass

The following tempting equivalences were explicitly rejected:

- rpm-ostree deployment rollback ≠ bootc previous-image recovery ≠ NixOS generation rollback.
- Transactional or atomic OS activation ≠ application/database transactionality.
- Previous operating-system content ≠ previous mutable user/data state.
- OCI artifact identity ≠ complete cryptographic trust chain.
- Declarative configuration/reproducible construction ≠ functional runtime correctness.
- Boot success ≠ service health ≠ SLO satisfaction.
- Retained deployment/generation history ≠ backup.
- Garbage collection/history pruning is not neutral: it can remove rollback capability.

No inspected primary source establishes AI as an independently trusted authority for production OS update promotion, reboot, rollback, trust-policy bypass or deletion of retained recovery states. Those authority claims remain unresolved.

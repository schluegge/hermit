# Supply-chain security and fuzzing baseline

Verification date: 2026-08-19

This file adds representative, primary-source-backed implementations for software-supply-chain integrity, repository-security assessment, continuous fuzzing, and bounded AI-assisted fuzzing. It extends the existing language-agnostic SDLC taxonomy; it does not create a claim of exhaustive security-tool coverage.

## 1. Supply-chain provenance — SLSA 1.2

### Baseline definition and SDLC role

Software provenance is verifiable information describing where, when, and how an artifact was produced. In the release/build lifecycle it connects an artifact to its source and build process so consumers can verify that the artifact was built according to expectations.

### Verified implementation/specification

SLSA version 1.2 is the current approved specification observed on 2026-08-19. Its Build Track defines increasing guarantees:

- Build L1: provenance exists.
- Build L2: signed provenance generated by a hosted build platform.
- Build L3: hardened build platform with stronger isolation/tamper resistance.

SLSA 1.2 also has a Source Track with progressively stronger source-control/process guarantees; do not conflate Build and Source levels.

### Selection and integration criteria

Use provenance when released artifacts need traceability to source/build inputs or when consumers need policy-verifiable build evidence. Select the target SLSA level based on threat model and build-platform guarantees, not marketing labels. Integrate provenance generation in the build platform and verification at release, package-consumption, deployment, or policy gates.

### Automation possibilities

Build systems can automatically emit provenance and downstream gates can automatically verify artifact digest, builder identity/build level, and expected build parameters. Provenance only provides value when it is actually verified against expectations.

- Build Track basics: https://slsa.dev/spec/v1.2/build-track-basics
- Build requirements: https://slsa.dev/spec/v1.2/build-requirements
- Artifact verification: https://slsa.dev/spec/v1.2/verifying-artifacts

## 2. Artifact signing and attestations — Sigstore / Cosign

### Baseline definition and SDLC role

Cryptographic signatures establish that an artifact was signed by the expected identity/key; attestations add signed semantic metadata that policy systems can evaluate. These are release/distribution integrity controls, not substitutes for testing or vulnerability analysis.

### Verified implementation

Sigstore documents Cosign as its recommended CLI for signing and verifying software artifacts. Current documentation verifies blobs and container images, supports keyless identity through OIDC, transparency-log-backed evidence, and in-toto attestations. `cosign verify-attestation` can verify attestations; current documentation also describes CUE/Rego policy validation.

### Selection and integration criteria

Choose identity/key mode based on deployment trust requirements. Pin the expected signer identity and OIDC issuer for keyless verification; do not use permissive wildcard identity matching as a production trust policy. Integrate signing after producing immutable release artifacts and verification before promotion/deployment/consumption.

### Automation possibilities

CI/CD can automatically sign release artifacts, publish verification bundles/attestations, and reject artifacts whose signature, identity, transparency evidence, or attestation policy fails verification.

### Sources

- Sigstore Cosign quickstart: https://docs.sigstore.dev/quickstart/quickstart-cosign/
- Signature verification: https://docs.sigstore.dev/cosign/verifying/verify/
- In-toto attestation verification: https://docs.sigstore.dev/cosign/verifying/attestation/

## 3. Repository and dependency security posture — OpenSSF Scorecard

### Baseline definition and SDLC role

Security-posture scanners automate checks over repository and dependency-development practices. They provide evidence and prioritization signals; they are not proofs that software is secure.

### Verified implementation

OpenSSF Scorecard is an automated tool that evaluates security-related repository heuristics. Current documented checks include CI tests, code review, branch protection, packaging, SAST, security policy, signed releases, token permissions and vulnerabilities, among others. It can run as CLI or GitHub Action and emit machine-readable JSON.

### Critical caveat

The Scorecard maintainers explicitly state that checks are opinionated heuristics with possible false positives and false negatives, and that Scorecard is not a definitive one-size-fits-all requirement. Therefore an aggregate score must not be treated as a security proof.

### Selection and integration criteria

Use individual checks that map to the project's threat model and workflow. Prefer structured per-check evidence over a single aggregate score when creating policy gates. Record exceptions where automated detection cannot understand legitimate project context.

### Automation possibilities

Run Scorecard periodically and/or in repository automation, consume structured results, alert on regressions, and gate narrowly defined high-risk requirements when the check is applicable and understood.

### Sources

- OpenSSF Scorecard maintainer repository: https://github.com/ossf/scorecard
- Check documentation: https://github.com/ossf/scorecard/blob/main/docs/checks.md
- Beginner supply-chain checks: https://github.com/ossf/scorecard/blob/main/docs/beginner-checks.md

## 4. Continuous fuzzing — OSS-Fuzz / CIFuzz

### Baseline definition and SDLC role

Fuzzing executes software against generated or mutated inputs to expose crashes, memory errors and other unexpected behavior. It complements unit/integration/property tests because it explores input spaces that deterministic examples may not cover.

### Verified implementation

OSS-Fuzz combines modern fuzzing engines with sanitizers and distributed execution. Current documentation lists libFuzzer, AFL++, Honggfuzz and Centipede and supports C/C++, Rust, Go, Python, Java/JVM, JavaScript and Lua. Closed-source/ineligible projects are directed toward self-hosted ClusterFuzz or ClusterFuzzLite rather than OSS-Fuzz itself.

CIFuzz integrates fuzz targets into pull-request CI. It builds fuzzers for the tested revision, runs them for a bounded period, reports reproducible newly introduced crashes, exposes the crashing input, and fails the CI check when criteria are met.

### Selection and integration criteria

Prefer fuzz targets that live with source, build with the normal test system, maintain seed corpora/dictionaries when useful, and run with relevant sanitizers. CI fuzzing is intentionally time-bounded; longer-running continuous fuzzing complements it. A passing bounded fuzz run proves only that no qualifying failure was found in that run.

### Automation possibilities

Automate fuzz-target builds, sanitizer execution, corpus reuse, crash reproduction, regression detection, SARIF/report upload and triage routing. Maintain deterministic reproduction artifacts for discovered crashes.

### Sources

- OSS-Fuzz documentation: https://google.github.io/oss-fuzz/
- CIFuzz continuous integration: https://google.github.io/oss-fuzz/getting-started/continuous-integration/
- Ideal integration guidance: https://google.github.io/oss-fuzz/advanced-topics/ideal-integration/

## 5. AI-assisted fuzzing — bounded research evidence

### Verified evidence

OSS-Fuzz documents research using LLMs to generate or modify fuzz targets. The research loop uses Fuzz Introspector to identify under-fuzzed functions, asks an LLM to generate targets, compiles/runs the result, measures coverage/crashes, and may iterate on compiler errors. Quality is judged by executable evidence such as compilation success, correct API usage, crash behavior and new coverage.

The same documentation describes this as research with explicit future-work items, including broader language coverage and eventual integration. Therefore it is evidence that AI can assist fuzz-target generation; it is not evidence that arbitrary LLM-generated fuzzing code is trustworthy without build/run/coverage verification.

OSS-Fuzz bug-fixing guidance also documents AI-proposed patches, but threat-model-based human/technical validation remains necessary; a proposed patch is not equivalent to a verified fix.

### Automation boundary

A safe baseline is: AI may propose fuzz targets or fixes, but deterministic compiler, sanitizer, fuzzing, reproduction and regression gates remain authoritative. Generated targets that do not compile, do not call the intended API, immediately produce invalid false-positive behavior, or fail to increase useful coverage must not be accepted merely because an AI produced them.

### Sources

- LLM fuzz-target generation research: https://google.github.io/oss-fuzz/research/llms/target_generation/
- Bug-fixing guidance: https://google.github.io/oss-fuzz/advanced-topics/bug-fixing-guidance

## Contradiction and scope boundaries

- SLSA provenance and Sigstore signatures/attestations are complementary: SLSA defines supply-chain guarantees/provenance requirements; Sigstore provides signing/verification mechanisms. Neither alone proves functional correctness or absence of vulnerabilities.
- Scorecard is a heuristic posture assessment, not a formal security certification.
- Fuzzing finds only failures reached by targets, corpora, engines, sanitizers and time budgets used; a green fuzz run is not proof of absence of defects.
- AI-generated fuzz targets and patches remain proposals until deterministic build/test/fuzz/reproduction evidence validates them.
- SLSA draft tracks beyond approved v1.2 material were not promoted into this baseline.
